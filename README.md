# 1c-deploy-agent

[<img src="docs/infostart-logo.svg" alt="Infostart" height="28">](https://infostart.ru/1c/articles/2784168/)

Разбор конвейера, схемы и примеры сеансов доставки — в статье на Инфостарте:
[«Конвейер доставки 1С там, где нет SSH: RDP-диск как транспорт»](https://infostart.ru/1c/articles/2784168/).

Конвейер доставки конфигураций 1С для контуров, где до сервера есть только RDP.

Агент работает в RDP-сессии на сервере 1С и получает команды через файлы на диске рабочей
станции, проброшенном в эту сессию (`\\tsclient\F\...`). Никаких открытых портов, служб
и агентов на сервере: только PowerShell, штатный пакетный Конфигуратор, `ras`/`rac` и COM.
Оркестратор на рабочей станции кладёт команду в папку, агент исполняет её и кладёт ответ.

Обкатано на живых базах: хранилище конфигурации на тестовом сервере, боевая база за шлюзом
удалённых рабочих столов, бухгалтерия без хранилища с доработками в расширениях.

## Когда это нужно

- До сервера 1С нет ни SSH, ни WinRM, ни WMI, ни общих папок. Есть RDP через шлюз и всё.
- Хочется автоматизировать рутину: обновить тестовую из хранилища, захватить объекты,
  наложить сборку, поместить версию, обновить боевую, поставить расширение, снять выгрузку.
- Установить на сервер что-то своё (OneScript, Jenkins-агент, vanessa-runner) нельзя или
  долго согласовывать, а PowerShell и платформа уже есть.

Если у вас есть SSH или хотя бы WinRM, посмотрите сначала на штатный режим агента
Конфигуратора (`/AgentMode`) и на [vanessa-runner](https://github.com/vanessa-opensource/vanessa-runner):
они закрывают вызовы платформы лучше. Здесь ценность в транспорте, а не в вызовах.

## Как устроено

```
 рабочая станция                          RDP-сессия на сервере 1С
 ─────────────────────────────            ─────────────────────────────────────────
 deploy.ps1  ──пишет──▶ F:\deploy\test\in\<id>.json
                                          deploy-agent.ps1 читает \\tsclient\F\deploy\test\in\
                                            │  1cv8.exe DESIGNER /S … /ConfigurationRepository…
                                            │  ras.exe + rac.exe  (сеансы ИБ)
                                            │  cscript mcp-daemon.vbs  (V83.COMConnector)
                                          пишет \\tsclient\F\deploy\test\out\<id>.json
 deploy.ps1  ◀─читает── F:\deploy\test\out\<id>.json
```

Одна папка обмена на все роли; у каждой роли (`test`, `prod`, `acc`, любое имя из конфига)
свои подпапки `in`/`out`. Крупные файлы (снимки `.cf`, сборки, расширения, выгрузки) ходят
через общую `artifacts\`.

## Состав

| Файл | Где работает | Назначение |
|---|---|---|
| `deploy-agent.ps1` | RDP-сессия сервера | Опрашивает папку обмена, исполняет команды, отвечает JSON |
| `agent-start.ps1`, `agent-start.cmd` | RDP-сессия сервера | Лаунчер: диагностика старта, автозагрузка профиля, запуск агента |
| `deploy.ps1` | рабочая станция | Оркестратор: кладёт команду, ждёт ответ, пишет `log\deploy.log` |
| `rdp-open.ps1` | рабочая станция | Необязательно: поднимает RDP-сессию и запускает лаунчер через Win+R |
| `mcp-daemon.vbs` | сервер, запускает агент | Необязательно: MCP-транспорт к базе по COM без клиента 1С |
| `mcpq.py` | рабочая станция | Необязательно: клиент к MCP-транспорту через папку обмена |
| `agent-config.sample.json` | — | Образец конфига; рабочая копия с учётными данными лежит в папке обмена и в git не попадает |
| `examples/` | — | Обезличенные примеры: `objects.xml`, `MergeSettings.xml`, файлы команд и ответов, сеанс доставки, скрипт для `com-exec`, аргументы для `mcpq.py` |

## Установка

1. На рабочей станции заведите корень папки обмена, например `F:\deploy`, и скопируйте
   туда файлы репозитория. Диск `F:` должен пробрасываться в RDP-сессию (клиент RDP:
   Локальные ресурсы, Подробнее, Диски). Буква диска любая, тогда поправьте `-ShareRoot`
   у агента и `-Root`/`DEPLOY_ROOT` у оркестратора.
2. Скопируйте `agent-config.sample.json` в `agent-config.json` и заполните секции.
   Имя секции = роль агента = `-Target` оркестратора.
3. Откройте RDP-сессию к серверу под учёткой, которой разрешён пакетный Конфигуратор,
   и запустите лаунчер двойным кликом по `\\tsclient\F\deploy\agent-start.cmd`
   (или `agent-start.cmd prod`, если роль не определяется по имени машины).
   Окно агента закрывать нельзя: в нём он и работает. Сессию можно отключить (не выйти).
4. На рабочей станции: `powershell -File F:\deploy\deploy.ps1 ping`.

Платформа на сервере должна быть **строго версии кластера**; старший клиент на пакетных
операциях падает с «несоответствие версий клиента и сервера». `platformVersion: "auto"`
берёт старшую установленную и годится только для первого `ping` на незнакомой машине:
он возвращает список установленных версий, из них вписывается точная.

## Конфиг

Секция роли в `agent-config.json`:

| Ключ | Назначение |
|---|---|
| `hostPattern` | Регулярное выражение по имени машины для автоопределения роли (иначе `-Role`) |
| `server1c`, `ib`, `ibUser`, `ibPassword` | ИБ и пользователь для пакетного Конфигуратора |
| `repoPath`, `repoUser`, `repoPassword` | Хранилище конфигурации. Пусто, если хранилища нет: команды `pull`/`test`/`commit`/`unlock`/`update-prod`/`repo-bind`/`repo-unbind` отключаются |
| `platformVersion` | Версия платформы (`8.3.24.1808`) или `auto` |
| `rasPort`, `clusterAddr` | Локальный `ras` поднимается на `rasPort` и смотрит на `clusterAddr` (кластер может быть на другой машине) |
| `mcpExchange`, `mcpEpf`, `mcpEpfServer` | MCP-транспорт: папка обмена глазами сервера, имя обработки, путь к ней глазами `rphost` (только если кластер не на машине агента) |
| `mcpLocalDir` | Куда агент кладёт локальную копию обработки для `rphost`, когда кластер на той же машине (по умолчанию `C:\ProgramData\deploy-agent\mcp`) |
| `dumpDir` | Каталог на диске сервера под `.dt` |

Пароли с кавычкой поддерживаются: агент оборачивает их по правилам `CommandLineToArgvW`.

Всё остальное, что зависит от контура, задаётся параметрами, а не правкой кода: корень папки
обмена (`-ShareRoot` у агента, `-Root` или `DEPLOY_ROOT` у оркестратора), период опроса
(`-PollSeconds`), таймаут ожидания ответа (`-TimeoutSec` у оркестратора, иначе таблица ниже).
В коде зашиты только стандартные пути платформы (`C:\Program Files\1cv8\<версия>\bin`) и
стандартные порты кластера для `com-check` (1540, 1541, 1560).

## Команды

`powershell -File F:\deploy\deploy.ps1 <команда> [-Target <роль>] [параметры]`

Служебные:

| Команда | Что делает | Таймаут |
|---|---|---|
| `status` | Свежесть heartbeat агента (локально, без команды) | — |
| `ping` | Версия агента, роль, хост, платформа, список установленных платформ | 90 с |
| `sessions [-Ib]` | Сеансы ИБ через `ras`/`rac`, без снятия | 90 с |
| `kill-sessions [-Ib]` | Снять все сеансы ИБ | 90 с |
| `com-check -Server1c <хост> [-Ib -IbUser -IbPassword]` | Достижимость ИБ по COM с этой машины: TCP до 1540/1541/1560, версия `comcntr`, CLSID/AppID, учётка службы, одно внешнее соединение | 180 с |
| `peek -Path <путь> [-Tail N]` | Каталог на сервере списком, файл хвостом | 90 с |
| `fetch -Path <путь> [-Name]` | Файл с диска сервера в `artifacts` (копирует сам агент, сверяет размер) | 5400 с |
| `com-exec -ScriptFile <.vbs>` | Выполнить VBScript на сервере (работа с ИБ через `V83.COMConnector`) | 180 с |
| `windows` | Все окна процессов 1С, включая дочерние и диалоги | 90 с |
| `screenshot` | Снимок экрана RDP-сессии в `log\screen.png` | 90 с |
| `build-epf -Src <XML> -Out <.epf>` | Сборка внешней обработки платформой сервера | 900 с |
| `reload` | Перезапуск агента на новую версию из папки обмена, без Win+R | 90 с |
| `stop` | Остановить агента | 90 с |

Хранилище конфигурации (`repoPath` задан):

| Команда | Что делает | Таймаут |
|---|---|---|
| `pull` | Снять сеансы, `ConfigurationRepositoryUpdateCfg -force`, `UpdateDBCfg`, `DumpCfg` в `artifacts\snapshot-<штамп>.cf` + SHA256 | 5400 с |
| `test [-Method mergecfg\|loadcfg\|loadfiles]` | Снять сеансы, `ConfigurationRepositoryLock` по `objects.xml`, наложить `release.cf`, `UpdateDBCfg`. **Захватывает объекты в хранилище** | 3600 с |
| `commit -Comment "…"` | `ConfigurationRepositoryCommit` по `objects.xml`, затем `Unlock` остаточных. **Помещает версию** | 3600 с |
| `unlock` | `ConfigurationRepositoryUnlock -force` по `objects.xml` без помещения (откат) | 900 с |
| `update-prod -Mode hot\|full` | Только роль `prod`. Бэкап `DumpCfg` в `artifacts\prod-backup-*.cf`, затем `hot` (`UpdateDBCfg -Dynamic+`, стоп, если динамически не применилось) или `full` (снять сеансы, обновить монопольно) | 5400 с |
| `repo-bind` | `ConfigurationRepositoryBindCfg -forceBindAlreadyBindedUser` под учётной записью из конфига; с `-Force` добавляет `-forceReplaceCfg` и `UpdateDBCfg`. Заменяет ручное подключение базы к хранилищу в Конфигураторе. Вручную нужна редко: `pull`, `test`, `commit`, `unlock` и `update-prod` чинят связь сами | 1800 с |
| `repo-unbind` | `ConfigurationRepositoryUnbindCfg -force`: снять связь с хранилищем, чтобы следующий `pull` привязал базу под пользователем из конфига | 1800 с |
| `repo-report -NBegin <N> [-NEnd <M>]` | `ConfigurationRepositoryReport … -ReportFormat txt`: история хранилища с версии N (кто, когда и какие объекты помещал). Текст в ответе и файлом в `artifacts`. Базу не меняет, сеансы не снимает | 900 с |
| `repo-dump -Version <N>` | `ConfigurationRepositoryDumpCfg … -v N`: конфигурация версии N хранилища в `artifacts\repo-vN-*.cf` + SHA256. Базу не меняет. Для восстановления объекта, затёртого в хранилище, из его прежней версии | 3600 с |
| `load-cf -Ib -IbUser -IbPassword [-Cf]` | Полная замена конфигурации произвольной ИБ кластера файлом из `artifacts` | 5400 с |

База без хранилища (расширения, выгрузки):

| Команда | Что делает | Таймаут |
|---|---|---|
| `ext-list` | Какие расширения стоят в базе (`DumpConfigToFiles -AllExtensions` во временный каталог) | 1800 с |
| `ext-dump -Extension <имя>` | Расширение в `.cfe` в `artifacts` | 900 с |
| `ext-install -Extension <имя> -Cfe <файл> [-NoBackup] [-Kill]` | Доставка `.cfe`, бэкап прежней версии, `LoadCfg -Extension`, отдельным запуском `UpdateDBCfg -Extension` | 3600 с |
| `dump-cf` | Конфигурация базы в `.cf` в `artifacts` + SHA256 | 5400 с |
| `dump-dt -Kill [-Dir]` | `DumpIB` монопольно; файл остаётся на сервере, забирается `fetch` | 21600 с |

MCP-транспорт (см. ниже):

| Команда | Что делает | Таймаут |
|---|---|---|
| `mcp-start [-AllowCode] [-Kill] [-Force] [-Exchange] [-Epf] [-EpfServer]` | Поднять демон по COM для ИБ роли | 300 с |
| `mcp-list` | Работающие демоны и окна 1С | 90 с |
| `mcp-stop` | Снять демоны | 90 с |

Параметры `-Ib -IbUser -IbPassword` у команд базы перекрывают конфиг: команда пойдёт в другую
базу того же кластера.

## Типовой цикл доставки через хранилище

1. `pull`: тестовая база обновлена из хранилища, снимок `snapshot-*.cf` в `artifacts`.
   Из снимка на рабочей станции собирается сборка: `release-<штамп>.cf` (снимок плюс ваши
   объекты), `objects-<штамп>.xml` (список на захват) и `MergeSettings-<штамп>.xml`
   (настройки объединения). Сборка вне этого репозитория: у каждого свой процесс
   (Конфигуратор, `ibcmd config import files`, EDT).
2. `test`: захват по `objects.xml`, объединение `release.cf`, применение. Объекты остаются
   захваченными. Проверяете тестовую базу руками или автотестами.
3. `commit -Comment "…"` при успехе, `unlock` при провале.
4. `update-prod -Mode hot` в рабочее время или `-Mode full` в окно.
5. Снова `pull`: убедиться, что в хранилище лежит именно то, что помещали.

Формат `objects.xml` для `Lock`/`Commit` (атрибут `includeChildObjects` обязателен):

```xml
<?xml version="1.0" encoding="UTF-8"?>
<Objects xmlns="http://v8.1c.ru/8.3/config/objects" version="1.0">
  <Object fullName="CommonModule.МойМодуль" includeChildObjects="true"/>
  <Object fullName="Document.МойДокумент" includeChildObjects="true"/>
  <Configuration includeChildObjects="false"/>
</Objects>
```

Корень `<Configuration/>` нужен, когда добавляется новый объект метаданных (меняется состав
конфигурации).

Три способа наложить `release.cf` в `test`:

- `mergecfg` (по умолчанию): `/MergeCfg -Settings -Objects`. Единственный, проверенный на
  живом хранилище.
- `loadcfg`: `/LoadCfg` целиком. Быстро, но база на поддержке хранилища его отвергает
  («изменение конфигурации запрещено»).
- `loadfiles`: `release.cf` во временную файловую базу, `DumpConfigToFiles -Objects`,
  `LoadConfigFromFiles`. Спасает, когда XML рабочей станции новее платформы сервера.

## Протокол обмена

- Команда: `<роль>\in\<id>.json`, `{ "id", "command", "created", ...параметры }`.
  Файл пишется как `.tmp` и переименовывается, чтобы агент не прочитал половину.
- Ответ: `<роль>\out\<id>.json`, `{ "id", "status": "ok"|"error", "error", "steps": [...] }`.
  Обработанная команда переезжает в `in\done\`.
- Heartbeat: `<роль>\out\agent-status.json` раз в 60 секунд.
- Единственность: `<роль>\out\agent.lock` с PID; новый экземпляр вытесняет старый (`reload`).
- Логи: агент пишет локально (`%TEMP%\deploy-agent\`), после каждой команды копирует
  в `log\agent-<роль>.log`.
- Таймаут оркестратора означает «состояние неизвестно», а не «не выполнилось»: агент
  продолжает работать. Не повторяйте команду, проверьте `status` и лог.

Артефакты в `artifacts\` тоже появляются атомарно: сначала `.tmp`, потом переименование.

## MCP-транспорт по COM

Нужен, когда ИИ-агенту (или любому инструменту на рабочей станции) нужны данные базы,
а HTTP-сервис опубликовать нельзя. Схема: внешняя обработка с ядром MCP открывается во
внешнем соединении (`V83.COMConnector`), демон `mcp-daemon.vbs` перекладывает JSON-RPC
из `<папка обмена>\in` в обработку и ответы в `<папка обмена>\out`. Клиент 1С не нужен,
лицензия тратится одна (на внешнее соединение).

Контракт обработки (её в репозитории нет, ядро MCP у каждого своё):

- экспортный метод модуля объекта `ProcessMCPRequest(ТелоЗапроса)`, принимает строку
  JSON-RPC, возвращает строку ответа;
- необязательный `EnableCodeExecution(Истина)`: включает выполнение произвольного кода,
  вызывается только при `mcp-start -AllowCode`;
- имена методов **латинские**: VBScript не вызывает кириллические идентификаторы, а
  `CallByName` в нём нет (это функция VBA). Для ядра с кириллическим именем заведите
  экспортную обёртку.

Клиент с рабочей станции: `set MCP_EXCHANGE=F:\mcp-test` и `python mcpq.py execute_query args.json`.

## Что выяснилось на практике

Ради этого раздела репозиторий и опубликован. Всё проверено на живых базах.

**Транспорт и RDP**

- Построчная запись лога в `\\tsclient` занимает около 10 секунд на строку. Лог пишется
  локально и копируется целиком.
- Чтение `.cf` через `\\tsclient` растягивает `MergeCfg` с 20 секунд до получаса:
  объединение читает файл многократно. Агент копирует `release.cf` (и `.cfe`, и снимки)
  на локальный диск перед любой операцией платформы.
- Канал редиректа диска даёт около 1 МБ/с. Выгрузка `.dt` на десятки гигабайт едет часами:
  `dump-dt` оставляет файл на сервере, `fetch` забирает его отдельно.
- `\\tsclient` у процесса, запущенного через `com-exec`, может смотреть в **другую**
  RDP-сессию того же пользователя: копирование отработает без ошибок и запишет файл мимо
  рабочей станции. Поэтому файлы копирует только сам агент (`fetch`).
- Политика запуска `.ps1` из Win+R или контекстного меню на некоторых серверах
  заблокирована, окно с ошибкой закрывается мгновенно. Лаунчер `.cmd` с
  `-ExecutionPolicy Bypass` держит окно открытым, а причина раннего выхода пишется в
  `log\start-fail-<хост>.log`.
- Скрипты для сервера храните в UTF-8 с BOM, `.vbs` для `cscript` в ANSI (агент конвертирует
  демон сам), вывод `cscript` читайте в кодировке 866.

**Пакетный Конфигуратор**

- Закрытое окно Конфигуратора не равно завершённому сеансу. Перед каждой пакетной
  операцией агент снимает сеансы через `rac`.
- Неудачные входы блокируют пользователя ИБ. Учётные данные не перебираются:
  одна попытка, и стоп.
- `LoadCfg` и `UpdateDBCfg` в одном запуске платформа не принимает («Ошибка в параметрах
  командной строки»), нужны два запуска.
- `/ConfigurationRepositoryReport` на большом хранилище идёт долго, поэтому в `pull` версия
  не через него, а через SHA256 снимка `.cf`. Как отдельная диагностика отчёт вынесен в
  команду `repo-report` со своим таймаутом.
- **Объединение обычной (неуправляемой) формы берёт её из файла целиком — слить построчно
  нельзя.** Если `release.cf` собран от снимка, устаревшего к моменту захвата, `test`+`commit`
  затрут чужую правку формы, попавшую в хранилище позже, и по размеру двоичного `Form` в git
  это незаметно. Поэтому перед `test` сверяйте историю: `repo-report -NBegin <версия снимка+1>`;
  чужие версии по захватываемым объектам — стоп и свежий `pull`. Затёртую версию достаёт
  `repo-dump -Version <N>`.
- `Commit` не отпускает объекты из списка, которые по факту не изменились: после `Commit`
  всегда `Unlock -force`.
- «База данных не открыта» на операциях с хранилищем при живой ИБ (сама база открывается,
  `dump-cf` проходит) означает, что файл хранилища держат зависшие процессы `1cv8.exe` от
  прошлых пакетных запусков, а не ИБ. Снятие сеансов через `rac` тут не помогает — сеансов нет;
  снимать нужно сами процессы, а если они в чужой RDP-сессии, у агента на это нет прав.
- Пакетный Конфигуратор подключается к кластеру только совпадающей версией платформы:
  8.3.22 к кластеру 8.3.24 даёт «Различаются версии клиента и сервера». `platformVersion`
  в конфиге держите равной версии кластера.
- Штатного «перечислить расширения» нет: `DumpConfigToFiles -AllExtensions` во временный
  каталог и чтение имён.
- `UpdateDBCfg -Extension` при несовпадении версии типовой падает с «Значение
  контролируемого свойства … не совпадает» и оставляет базу в промежуточном состоянии
  (`LoadCfg` прошёл). Лечится обратной установкой автобэкапа с `-NoBackup`. Расширение
  собирайте на той же версии типовой, что стоит в боевой.
- Динамическое обновление боевой (`-Dynamic+`) при активных сеансах останавливается на
  реструктуризации. Агент это распознаёт по тексту платформы (русская локаль, шаблоны
  в начале `Do-UpdateProd`) и не переключается на `full` сам: решение за человеком.
- Связь базы с хранилищем рвётся при перезаливке базы из `.dt` («Пользователь существующей
  связи отличается от текущего»). С версии 2.1 агент лечит это сам: разбирает текст ошибки
  платформы, выполняет `ConfigurationRepositoryBindCfg -forceBindAlreadyBindedUser` под
  учётной записью из конфига и один раз повторяет упавший шаг. Работает в `pull`, `test`,
  `commit`, `unlock` и `update-prod`; замена конфигурации базы хранилищной
  (`-forceReplaceCfg`) включается только внутри `pull` и только вне роли `prod`. Отдельно
  связь ставится командой `repo-bind`. Отказ «Пользователь уже аутентифицирован в хранилище»
  это не лечит: там залипла сессия учётной записи в файловом хранилище, нужен другой
  пользователь или ожидание.
- Внешняя обработка, собранная старшей платформой рабочей станции, на младшей платформе
  сервера молча не открывается («Неизвестная версия формата»). Для сервера собирайте
  его платформой: `build-epf`.

**COM и MCP**

- `.epf` открывает **сервер 1С** (`rphost`), а не скрипт. Проброшенный `\\tsclient` серверу
  не виден: обработка обязана лежать на диске, доступном `rphost`. Если кластер на другой
  машине, путь задаётся вручную (`mcpEpfServer`).
- `rphost` кэширует внешнюю обработку **по пути к файлу**. Перезаписанный `.epf` под тем же
  именем сервер отдаёт в старой редакции (COM-ошибка 438 на новых методах). Обновляя
  обработку, меняйте имя файла.
- PowerShell с объектами 1С по позднему связыванию не работает (свойства приходят `$null`);
  для COM используется VBScript.
- Ключ `/Execute` в некоторых конфигурациях обработку подключает, но форму не открывает,
  а обработчик ожидания формы в пакетно запущенном клиенте не тикает. Поэтому демон
  по COM, а не клиент.
- Каждое внешнее соединение занимает клиентскую лицензию, первое соединение к большой базе
  устанавливается около минуты. Лишних демонов не держите.
- Снятие сеансов (`pull`, `test`, `load-cf`) рвёт COM-соединение демона. Демон один раз
  переподключается и повторяет запрос; если не вышло, отвечает ошибкой и завершается,
  чтобы `mcp-list` не показывал зомби.

## Ограничения

- Windows, Windows PowerShell 5.1, платформа 8.3 (проверено на 8.3.22, 8.3.24, 8.3.27).
  Тексты платформы разбираются в русской локали.
- Агент живёт, пока жива RDP-сессия. Отключение сессии (без выхода) его не убивает;
  перезагрузка сервера убивает, дальше нужен человек с RDP-клиентом или `rdp-open.ps1`.
- Команды исполняются строго по одной. Длинная выгрузка занимает агента целиком.
- Сборка `release.cf` из исходников в репозиторий не входит.
- Никакой аутентификации в папке обмена: кто пишет на диск рабочей станции, тот и
  командует агентом. Это осознанно: диск и так ваш.
